# Media assets

`MediaAsset` is the foundation for associating images, videos, infographics, and
documents with a post. It records whether material was generated by us, supplied
as an official release, or uploaded directly, together with its origin, license,
location, optional thumbnail, and structured metadata.

## Official Images First

The existing OpenAI and Google RSS/Atom collectors inspect image enclosures,
Media RSS image content/groups, primary Open Graph/Twitter image references,
and images inside `main`/`article` on the linked official release page. Anthropic
still has no approved feed and remains unchanged. No image search, unrelated
article scraping, image-byte downloads, new storage, or video support is added.

Page hosts are fixed by the collector. Additional image/CDN hosts and reviewed
permissions are configuration, not claims supplied by the remote page. HTTPS,
exact host matching, bounded documents (2 MiB), ten-second request timeouts and
redirect validation apply to source fetches. Unapproved entry links are never
fetched. Site chrome and explicitly tiny HTML images are ignored. Metadata is
candidate evidence, not a guarantee of file dimensions or downstream availability.

### Usage permission

Official hosting alone does **not** grant reuse rights. An image is selectable
only with either an explicit image-scoped Media RSS CC0 license or a reviewed
permission for its **exact image URL** in `OFFICIAL_IMAGE_POLICIES`. A page-wide
license link is not treated as an image license. Configured denials override RSS
licenses. No default commercial reuse permission is assigned to OpenAI or Google.

Example schema (illustrative URLs; not an actual permission grant):

```json
{
  "OpenAI": {
    "image_hosts": ["approved-cdn.example"],
    "permissions": {
      "https://approved-cdn.example/release.jpg": {
        "usage_allowed": true,
        "license_type": "reviewed_editorial_permission",
        "terms_url": "https://openai.com/permission-evidence",
        "evidence": "Record of permission covering this exact image and Telegram reuse",
        "attribution_required": false,
        "attribution": null
      }
    }
  }
}
```

Set the environment variable to a JSON object, keyed by collector source (`OpenAI`
or `Google`). Include only verified CDN hosts and permission records reviewed for
the intended use. Query strings on image URLs are preserved, including signatures;
grants do not automatically cover different URLs. Required visible credits are
supported only with a non-empty `attribution` string and explicit reuse permission.
The existing Publisher appends that exact plain-text credit to the Telegram
caption and checks both the Gateway wire-string length and Telegram UTF-16 length
against the 1024-character budget. Factory and Adapter share
`TelegramPublisher.prepare_publication`: fitting HTML stays unchanged; otherwise
it tries the complete plain text with `parse_mode=null`, then removes only
redundant ASCII spaces/tabs and extra blank lines from the news. It retains every
sentence, non-empty line and paragraph in order. Credit is never normalized or
truncated. If no complete variant fits, preparation fails before any Gateway
request. Post and ContentVariant are never rewritten. Text-only publications keep
the existing strict HTML behavior. No additional AI calls are made.
A license name or credit alone without evidence and an explicit allowed flag is
insufficient. The legacy single-image resolver input also requires the `usage`
permission object.

### Existing pipeline and persistence

`NewsItem.official_images` holds typed candidates with page/file URLs, source,
discovery method, trusted image hosts, discovery time, and optional permission.
`image_discovery_status` distinguishes `complete`, `temporary_error`, and the
backwards-compatible `not_checked` default for manually supplied news.
Normalization preserves this evidence and does not rewrite signed media URLs.

The intelligence bridge passes this evidence to the existing pure `MediaResolver`.
The first permitted official image wins; no AI provider is invoked. The existing
`MediaAsset` stores the image URL, source=`official`, origin, license and complete
source/usage evidence in its JSON metadata, with `planning_status=reference_ready`.
It is usable by the existing image Publisher without changing its transport.
The Publisher rechecks the stored usage permission before selecting official
media and carries any credit alongside the selected image. Page identity is
compared using the existing news canonicalization (including trailing slashes and
UTM parameters); original page/file URLs and provenance remain unchanged.
No blanket permissions for Google or OpenAI are introduced.

A completed lookup with no suitable permitted image uses the existing single
`generate_image` fallback plan. This change does not call any paid service during
tests or alter Gateway model selection, retry policy, storage or production config.
When a caller explicitly supplies a provider, the existing generation behavior
continues for a completed negative lookup.

A temporary release-page failure keeps the news item and any RSS candidates.
A valid licensed RSS image may still be selected. Otherwise the same `MediaAsset`
gets `planning_status=source_retry_required`, `generation_status=deferred`, a safe
error code and `generation_deferred=true`. Neither orchestration nor direct
`MediaGenerationService` execution may generate from that plan. A source outage
is not interpreted as absence. This stage adds no retry worker or backlog recovery;
retrying discovery/replanning is a later explicit operation. Existing Publisher
text-only fallback behavior is unchanged.

Existing infographic/document/video strategies outside this new image-candidate
contract remain unchanged; this stage does not add a way to publish them.

## Phase 3 generation execution

`MediaGenerationService` executes only the `generate_image` plans produced by
Phase 2. A caller supplies a prompt and an `ImageGenerationProvider`; the
provider owns vendor API calls and durable image storage and returns a public
URL. The service then changes the existing asset from `generation_required` to
`complete` and records the prompt, optional `ru`/`en` language, provider, and
provider metadata for auditability.

Execution is idempotent after an asset reaches `ready`: retrying returns the
stored asset without invoking the provider again. Provider errors are recorded
as `failed` and raised as `MediaGenerationError`, allowing a worker to decide
when to retry. Official references and uploaded media cannot enter generation.

Phase 3 adds provider-neutral orchestration only. It does not choose media
policy again, download official media, prescribe an image vendor or storage
backend, publish to a channel, or create a second publishing pipeline.
